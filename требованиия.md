# Лабораторная работа №4 — To-Do List и доступность интерфейса (Sass → Tailwind CSS)

## Описание

В этой лабораторной начинается новый сквозной проект курса — приложение **To-Do List**. Сначала вы создадите его на Sass и vanilla JS / jQuery, затем сделаете отдельную версию интерфейса на Tailwind CSS. Обе версии должны быть доступны для работы с клавиатуры и вспомогательных технологий. Проект продолжится в следующих лабораторных.

Оба задания выполняются **к одному дедлайну** в новом репозитории и сдаются двумя pull request. Работать над версиями можно в любом порядке и переключаться между ветками до сдачи.

## Цель работы

После выполнения работы вы сможете:

- реализовать список задач с поиском, редактированием и сохранением в `localStorage`;
- применять требования доступности к интерактивному интерфейсу и проверять его вручную и через Lighthouse;
- организовать стили приложения на Sass и перенести оформление на Tailwind CSS, сохранив поведение приложения.

## Краткая теория

### Что такое доступность и зачем она нужна

**a11y** — сокращение от *accessibility*: между «a» и «y» 11 букв (по той же схеме, что i18n — *internationalization*).

Доступный интерфейс нужен:

* незрячим и слабовидящим — они пользуются **скринридерами** и увеличением экрана;
* людям с нарушениями моторики — многие работают **только с клавиатуры**;
* людям с нарушениями цветовосприятия (дальтонизм) и чувствительностью к анимации;
* и всем остальным: тем, кто быстро работает с клавиатуры, сидит с ноутбуком на солнце или со сломанной мышкой. Бонусом — лучше SEO: поисковый робот тоже «не видит» картинок и `<div>`-кнопок.

Основной стандарт — **WCAG** (Web Content Accessibility Guidelines), ориентир для обычных сайтов — уровень **AA**. В России на его основе действует ГОСТ Р 52872-2019.

### Глоссарий

* **WCAG** — рекомендации W3C по доступности веб-контента. Уровни соответствия: **A** (минимум), **AA** (стандартный ориентир), **AAA** (максимальный).
* **Скринридер** — программа, которая озвучивает интерфейс и позволяет управлять им с клавиатуры или жестами: NVDA (Windows), VoiceOver (macOS, iOS), TalkBack (Android).
* **Фокус** — элемент, который сейчас принимает ввод с клавиатуры. Перемещается клавишами **Tab** / **Shift+Tab**; Enter / Space активируют кнопку, Esc обычно закрывает окно.
* **`:focus-visible`** — псевдокласс, срабатывающий, когда браузер считает нужным показать фокус (как правило, при навигации с клавиатуры, а не по клику мышью). Писать `outline: none` **без замены** нельзя: клавиатурный пользователь перестаёт понимать, где он находится.
* **Контраст** — отношение яркости текста и фона. По WCAG AA для обычного текста нужно **≥ 4.5:1**, для крупного (от 24px или от ~18.7px жирным) — **≥ 3:1**.
* **Доступное имя (accessible name)** — то, как элемент «называется» для скринридера. Берётся из текста внутри элемента, связанного `<label>`, атрибута `alt` у картинки или из `aria-label` / `aria-labelledby`. Кнопка-иконка без имени озвучивается просто как «кнопка».
* **ARIA** — атрибуты `role` и `aria-*`, которые сообщают вспомогательным технологиям то, чего не выразить HTML. Первое правило ARIA: **не используйте ARIA, если есть нативный HTML-элемент** — `<button>`, а не `<div role="button">`: нативная кнопка уже умеет фокус, Enter и Space.
* **`<dialog>`** — нативное модальное окно. Метод `showModal()` переносит фокус внутрь окна, делает остальную страницу неактивной (недоступной для клика и Tab) и закрывает окно по **Esc**.
* **Lighthouse** — инструмент Google для автоматического аудита страниц. В этой лабе используем панель **Lighthouse в Chrome DevTools** (то есть открываем проект в Google Chrome). Категория **Accessibility** даёт оценку 0–100 и список найденных проблем с пояснениями.
* **`aria-live`** — область страницы, изменения в которой скринридер озвучивает автоматически (например, «Задача добавлена»).

### Как проверять

1. **Lighthouse в Google Chrome.** Откройте страницу **через локальный сервер** (Live Server или `npx serve .`) → DevTools → вкладка *Lighthouse*. У панели есть три режима:

   | Mode | Что проверяет | Для чего подходит |
   |------|---------------|-------------------|
   | *Navigation* | Новую загрузку страницы: Lighthouse перезагружает её перед аудитом. | Первоначальная загрузка, в том числе показатели производительности. При включённой настройке *Clear storage* хранилище очищается перед аудитом, поэтому сохранённые задачи и тема исчезнут. |
   | *Timespan* | Промежуток взаимодействий: запустите запись, поработайте со страницей, остановите запись. | Производительность при действиях пользователя. **Категория Accessibility в этом режиме недоступна.** |
   | *Snapshot* | Текущее состояние страницы **без перезагрузки**. | Доступность заполненного списка, тёмной темы или открытой модалки — именно то, что нужно в этой лабе. |

   Для проверки A7 снимите галочку *Clear storage* в настройках панели, чтобы хранилище не очистилось во время серии проверок. Добавьте несколько задач, в том числе выполненную, затем выберите *Mode: Snapshot*, *Categories: Accessibility* и нажмите *Analyze page state*. Сделайте снимки списка в светлой и тёмной темах, каждый раз для *Desktop* и *Mobile*: всего четыре проверки в задании 1. Если в задании 2 оставлена одна тема, достаточно двух снимков — *Desktop* и *Mobile*. После этого откройте модалку и сделайте ещё один снимок, чтобы проверить элементы формы. Snapshot проверяет текущую страницу без перезагрузки, поэтому видит добавленные задачи и выбранную тему.
2. **Контраст.** DevTools → *Elements* → панель *Styles* → кликните на цветной квадратик у свойства `color`: в палитре показывается *Contrast ratio* и отметки AA/AAA. Проверяйте **в обеих темах**, если их две.
3. **Доступное имя.** DevTools → *Elements* → выделите элемент → панель *Accessibility* → *Computed Properties* → *Name*.
4. **Тест «без мыши».** Уберите мышь ~~в ящик~~ подальше и пройдите все сценарии только клавиатурой: Tab, Shift+Tab, Enter, Space, Esc.
5. *(по желанию)* Расширение [axe DevTools](https://www.deque.com/axe/devtools/) и настоящий скринридер (NVDA на Windows, VoiceOver на macOS).

> ⚠️ **Lighthouse 100 ≠ доступный сайт.** Автоматика находит только часть проблем: она не знает, куда должен уйти фокус после удаления задачи и закрывается ли модалка по Esc. Требования A1, A4 и A5 проверяются **только руками**.

## Задание 1 — To-Do List на Sass + vanilla JS / jQuery

### Постановка задачи

Создайте приложение To-Do List в новом репозитории. Пользователь должен управлять задачами, находить их по названию и возвращаться к сохранённому списку после перезагрузки страницы. Ориентируйтесь на макеты в разделе источников, но не копируйте их в ущерб доступности: если контраст в макете ниже 4.5:1, выполните требование A6.

### Функциональные требования

* Присутствует список задач. Каждая задача содержит:
  * чекбокс;
  * название задачи;
  * кнопки редактирования и удаления задачи.
* Присутствует кнопка добавления задачи; по нажатию открывается модальное окно с формой создания задачи.
* Задачу можно отредактировать (меняется название), удалить и отметить выполненной.
* Выполненная задача зачёркивается и перемещается в раздел выполненных или вниз списка.
* Поиск задачи по названию — список фильтруется динамически, по мере ввода.
* Переключение светлой / тёмной темы; выбранная тема сохраняется в `localStorage` (как в лабе №3).
* Адаптивность: интерфейс корректно выглядит на мобильных и десктопах.
* Задачи хранятся в `localStorage`: после перезагрузки страницы список, названия и отметки о выполнении сохраняются. Любое изменение (добавление, редактирование, удаление, отметка) сразу записывается в хранилище.

> Храните задачи массивом объектов, например `{ id, title, done }`, и сериализуйте его через `JSON.stringify` / `JSON.parse`. Если в хранилище пусто или лежит некорректный JSON, приложение должно стартовать с пустым списком, а не падать. `id` задачи сохраняйте вместе с ней: из него строятся `id` элементов для `aria-labelledby` (см. A2).

### Технические требования

* HTML5;
* Sass / SCSS с подходами лабы №3: модули `@use` / `@forward`, переменные и миксины, БЭМ, темы через CSS custom properties;
* vanilla JS или jQuery — на выбор;
* npm-проект: `sass` как dev-зависимость, скрипты `sass:dev` и `build`, `.gitignore` — как в лабе №3.

> Для JS-хуков используйте классы `js-*` или `data`-атрибуты, а не классы оформления (см. лабу №3). Во втором задании классы оформления заменятся на утилиты Tailwind — и JS при этом не сломается.

Требования A1–A7 действуют в обоих заданиях. Во втором задании переключение темы можно не переносить; соответствующие оговорки даны ниже.

Для действий используйте нативные интерактивные элементы (`<button>`, `<a>`, `<input>` и т. п.), а не `<div>` / `<span>` с обработчиком клика. Порядок перехода по Tab логичный. | Тест без мыши |

#### Пояснения и примеры

**A1 — клавиатура.** Если элемент что-то делает по клику — это `<button type="button">`. Не меняйте порядок Tab через `tabindex` больше нуля: порядок должен совпадать с порядком в разметке. Если редактирование сделано прямо в строке (без модалки), то Enter сохраняет, Esc отменяет, а фокус после этого возвращается на кнопку «Редактировать».

**A2 — имена кнопок.** Пять кнопок «Удалить» подряд для скринридера неразличимы — в имя кнопки нужно добавить название задачи. Название меняется при редактировании, поэтому важно, чтобы имя кнопки не «застряло» в старом варианте. Есть два способа.

*Способ 1 — `aria-labelledby` (рекомендуется).* Имя собирается из текста элементов, чьи `id` перечислены в атрибуте. Кнопка ссылается на саму себя (её имя — скрытый текст внутри) и на заголовок задачи:

```html
<li class="task" data-task>
  <input type="checkbox" id="task-7-done">
  <label for="task-7-done" class="task__title" id="task-7-title">Купить молоко</label>

  <button type="button" id="task-7-delete" aria-labelledby="task-7-delete task-7-title">
    <span class="visually-hidden">Удалить задачу</span>
    <svg aria-hidden="true" focusable="false">...</svg>
  </button>
</li>
```

Скринридер прочитает «Удалить задачу Купить молоко». Заголовок задачи — это `<label>` чекбокса (требование A3), поэтому клик по названию переключает выполнение. На этот же заголовок ссылаются кнопки. При переименовании достаточно поменять текст в `.task__title` — имена чекбокса и кнопок обновятся **сами**. Уникальные `id` генерируются один раз при создании задачи и сохраняются вместе с ней: если используете числовой счётчик, после загрузки списка начинайте с числа больше всех сохранённых `id`. `crypto.randomUUID()` работает только в безопасном контексте (например, HTTPS, `localhost` или `127.0.0.1`), поэтому на телефоне при открытии локального сервера по `http://192.168.x.x` может быть недоступен. Если редактирование сделано прямо в строке, не удаляйте элемент с `id` заголовка — иначе ссылка сломается.

*Способ 2 — `aria-label`.* Имя пишется в атрибут целиком, поэтому его нужно выставлять **при каждом изменении** названия:

```js
function setTaskTitle(item, title) {
  item.querySelector('.task__title').textContent = title;
  item.querySelector('.js-delete').setAttribute('aria-label', `Удалить задачу «${title}»`);
  item.querySelector('.js-edit').setAttribute('aria-label', `Редактировать задачу «${title}»`);
}
```

Способ удобен, если весь список перерисовывается из массива задач одной функцией: тогда `aria-label` задаётся в одном месте и всегда актуален. Опасен, если DOM правится точечно: текст поменяли, атрибут забыли.

> ⚠️ Не вставляйте название задачи в разметку через `innerHTML` и шаблонные строки: ввод пользователя вида `<img src=x onerror=alert(1)>` выполнится как код (XSS), а кавычка в названии сломает атрибут. Используйте `textContent` и `setAttribute` (в jQuery — `.text()` и `.attr()`).

**A3 — подписи.** Если подпись не нужна визуально, её прячут так, чтобы скринридер её всё равно читал (`display: none` для этого **не подходит**). Удобно оформить миксином из лабы №3:

```scss
@mixin visually-hidden {
  position: absolute;
  width: 1px;
  height: 1px;
  margin: -1px;
  padding: 0;
  overflow: hidden;
  clip-path: inset(50%);
  white-space: nowrap;
  border: 0;
}
```

```html
<label for="search" class="visually-hidden">Поиск задач</label>
<input id="search" type="search" placeholder="Найти задачу...">
```

**A4 — модальное окно.** `<dialog>` делает большую часть работы сам:

```html
<button type="button" class="js-add-task">Добавить задачу</button>

<dialog class="modal js-task-dialog" aria-labelledby="task-dialog-title">
  <form method="dialog">
    <h2 id="task-dialog-title">Новая задача</h2>
    <label for="task-title">Название</label>
    <input id="task-title" name="title" required autofocus>
    <button type="submit">Сохранить</button>
    <button type="button" class="js-close-dialog">Отмена</button>
  </form>
</dialog>
```

```js
const dialog = document.querySelector('.js-task-dialog');
document.querySelector('.js-add-task').addEventListener('click', () => dialog.showModal());
document.querySelector('.js-close-dialog').addEventListener('click', () => dialog.close());
```

`autofocus` ставит фокус в поле при открытии, Esc закрывает окно, фон становится недоступным. Современные браузеры при закрытии `<dialog>` сами возвращают фокус на элемент, который был в фокусе до открытия, — **проверьте это** тестом без мыши. Если модалка самописная (как в лабе №2), всё это — фокус внутрь, Esc, «ловушку» фокуса и возврат фокуса — придётся реализовать вручную.

Этот пример показывает управление окном; обработчик сохранения, который создаёт задачу из данных формы, нужно добавить отдельно.

**A5 — фокус после удаления.** Удалённый элемент исчезает из DOM, и фокус «падает» на `<body>` — следующий Tab начнётся с начала страницы. Если поиск скрыл часть задач, выбирать нужно среди **видимых** соседей:

```js
function deleteTask(item) {
  const tasks = [...document.querySelectorAll('[data-task]')];
  const index = tasks.indexOf(item);
  const isVisible = task => task.getClientRects().length > 0
    && getComputedStyle(task).visibility !== 'hidden';
  const next = tasks.slice(index + 1).find(isVisible)
    ?? tasks.slice(0, index).reverse().find(isVisible);
  item.remove();
  if (next) {
    next.querySelector('input[type="checkbox"], button').focus();
  } else {
    document.querySelector('.js-add-task').focus();
  }
}
```

**A6 — видимость.** Стили фокуса вы уже делали для компонента в лабе №3 — теперь они нужны **всем** интерактивным элементам. Проверьте, что обводка фокуса и зачёркнутый текст хорошо видны и в тёмной теме.

**A7 — Lighthouse.** Порог 90, а не 100: цель — не «закрасить цифру», а выполнить A1–A6. Проверяйте страницу с несколькими задачами, иначе аудит не увидит чекбоксы и кнопки управления. Если Lighthouse ругается — прочитайте пояснение к каждой проблеме, там есть ссылка на объяснение и способ исправления.

> **Для любопытных (не оценивается):** сообщения через `aria-live` («Задача добавлена», «Найдено задач: 3»), отключение анимаций при `prefers-reduced-motion: reduce`.

## Задание 2 — To-Do List на Tailwind CSS

### Постановка задачи

Сделайте самостоятельную Tailwind-версию приложения в ветке `lab-4-tailwind`. Повторите интерфейс и функциональность задания 1; переключение темы можно не переносить. Обе ветки должны существовать параллельно, чтобы преподаватель мог проверить их к одному дедлайну.

### Функциональные требования

* Сохранена функциональность задания 1, кроме переключения темы, если вы решили его не переносить.
* Переключение темы **можно не делать**. В этом случае из A1 выпадает сценарий «переключить тему», а A6 и A7 проверяются для единственной темы.

### Технические требования

* HTML5;
* Tailwind CSS (v4, сборка через `@tailwindcss/cli`);
* JS-логика из задания 1 (vanilla JS / jQuery).

Требования **A1–A7 сохраняются**. Полезные утилиты Tailwind:

* `sr-only` — визуально скрытая подпись (аналог миксина `visually-hidden`);
* варианты `focus-visible:` — стили фокуса, например `focus-visible:outline-2 focus-visible:outline-offset-2`;
* варианты `motion-reduce:` — отключение анимаций при `prefers-reduced-motion`.

#### Подключение Tailwind CSS

Не используйте Play CDN (`<script src="...@tailwindcss/browser">`): он предназначен только для прототипов. Собираем CSS через npm — так же, как Sass в лабе №3.

Работа ведётся в отдельной ветке `lab-4-tailwind`, созданной от стартового `main`. В этой ветке Sass не нужен: создайте Tailwind-версию приложения с той же функциональностью. JS-логику можно перенести из ветки `lab-4`; для этого не требуется ждать проверки или слияния её pull request.

Установите Tailwind и его CLI:

```bash
npm install -D tailwindcss @tailwindcss/cli
```

Создайте входной файл `src/input.css`:

```css
@import "tailwindcss";
```

Здесь `@import` — подключение Tailwind в обычном CSS, а не устаревший `@import` модульной системы Sass из лабы №3.

Если делаете переключение темы через атрибут `data-theme` (как в задании 1), добавьте в тот же файл вариант `dark:`, привязанный к атрибуту, — иначе Tailwind ориентируется только на системную тему:

```css
@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *));
```

Скрипты в `package.json`:

```json
{
  "scripts": {
    "tailwind:dev": "tailwindcss -i ./src/input.css -o ./dist/css/main.css --watch",
    "build": "tailwindcss -i ./src/input.css -o ./dist/css/main.css --minify"
  }
}
```

В `index.html` подключите **собранный** файл:

```html
<link rel="stylesheet" href="dist/css/main.css">
```

`.gitignore` — как раньше (`node_modules/`, `dist/`). Запуск при разработке — снова в два процесса: `npm run tailwind:dev` и локальный сервер.

> Tailwind сам находит классы в файлах проекта (HTML и JS) и кладёт в итоговый CSS **только использованные**. Поэтому в JS пишите имена классов целиком: `classList.add('line-through')` — сработает, `classList.add('line-' + 'through')` — нет. Файлы из `.gitignore` не сканируются.

Для оформления выполненной задачи можно оставить класс на элементе постоянным, а из JS менять только состояние: `task.dataset.done = 'true'` или `'false'`. Класс `data-[done=true]:line-through` на этом элементе применит зачёркивание при `data-done="true"`. Так JS не зависит от классов оформления.

### Примерная структура итогового проекта

```
todo/
├─ src/
│  └─ input.css        <-- подключение Tailwind
├─ js/
│  └─ main.js
├─ dist/               <-- собранный CSS (в .gitignore)
├─ index.html
├─ package.json
├─ package-lock.json
├─ README.md           <-- инструкция запуска обновлена
└─ .gitignore
```
